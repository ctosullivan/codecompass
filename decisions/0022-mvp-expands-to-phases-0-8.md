# 0022. MVP expands to phases 0-8

## Status

Accepted

## Context

The MVP milestone has been defined as phases 0-6 since project
scaffolding (`decisions/0008`, `planning/ROADMAP.md`), and all six are
now done. `decisions/0012` (conversational-first REPL design), recorded
later, reframed the REPL as "the actual product," with the markdown
digests generated by `sync` serving as backing store for it — a
significant shift from the original framing where digests themselves
were the deliverable. The MVP boundary was never revisited after that
reframing.

Separately, Phase 8 ("Single-vendor chat REPL," `planning/ROADMAP.md`)
is the first implementation of that framing, and it structurally depends
on Phase 7 ("Zero-question bootstrap & promote," `planning/phase-7-
bootstrap-and-promote.md`, `decisions/0017`-`0021`, currently `planned`,
not implemented): the REPL reads Skill files directly off disk and
consumes dual-audience (technical + conversational) content, both of
which are Phase 7 outputs. Phase 7's own plan explicitly restructures
those content fields away from Phase 5's current `context_path`-gated
`gap_analysis` shape. Shipping a v0.1 at the end of Phase 6, as currently
planned, would tag a milestone containing a `FULL`-depth mechanism
already scheduled for replacement in the very next phase, and none of
the consumption layer `decisions/0012` calls the actual product.

## Decision

The MVP milestone expands from phases 0-6 to phases 0-8. `v0.1` is
tagged only once Phase 8 is `done`, not Phase 6. Phases 0-6 remain done,
unchanged. Phase 7 and Phase 8 move from `planning/ROADMAP.md`'s
Post-MVP table into its MVP table, in that order — Phase 7 before Phase
8, matching the dependency between them.

## Alternatives considered

- **Ship v0.1 at the end of Phase 6 as originally planned, treat Phase
  7-8 as a v0.2 milestone.** Rejected — per `decisions/0012`, the REPL is
  the actual product; a v0.1 that ships none of it, alongside a
  `FULL`-depth mechanism already known to be replaced in-plan, risks
  tagging and documenting a release that's stale relative to the
  project's own stated design before anyone uses it.
- **Promote only Phase 8 into the MVP, leave Phase 7 post-MVP, and build
  the REPL against Phase 5's current `gap_analysis` output.** Rejected —
  Phase 8 already depends on Phase 7's Skill files and the dual-audience
  content shape Phase 7's plan restructures; building it against fields
  already scheduled for replacement creates near-term rework for no
  benefit, since Phase 7 is already fully planned.

## Consequences

- `CLAUDE.md` §6 and `CONTRIBUTING.md`'s mirrored text change "the MVP
  (phases 0-6)" to "the MVP (phases 0-8)" — the `CLAUDE.md` edit requires
  its own explicit approval before being written, per `CLAUDE.md` §0.
- `planning/ROADMAP.md`'s MVP table, "MVP done when" criteria, and
  Post-MVP table all update to reflect the new boundary — no phase gets
  renumbered, only table membership changes.
- The `v0.1` tag and dated `CHANGELOG.md` release section (`CLAUDE.md`
  §6's release-promotion step) stays deferred, now until Phase 8 is
  `done` instead of Phase 6. This decision does not itself trigger that
  step.
- `planning/phase-8-*.md` still needs to be written before Phase 8
  implementation can start, per `CLAUDE.md` §1 — unaffected by this
  decision beyond that phase now counting toward MVP completion.
- Post-MVP now starts at (already-renumbered) Phase 9 — unaffected in
  content, only in which table it's tracked under.
