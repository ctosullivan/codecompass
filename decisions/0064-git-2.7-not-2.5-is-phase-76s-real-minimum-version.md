# 0064. `decisions/0063` point 8 is superseded: Git 2.7, not 2.5, is Phase 76's real minimum version — a direct `git --version` check replaces the rejected alternative

## Status

Accepted (2026-09-28, corrective pass).

## Context

A post-closeout review of Phase 76 (already marked `done`) found that
`decisions/0063` point 8's claim — "no Git feature newer than `git
worktree`/`--git-common-dir` themselves (Git 2.5, July 2015) is ever
required" — is false for the actual command set `git_topology.py` calls
unconditionally on every `detect_git_topology` invocation.

Verified directly against Git's own release notes
(`/usr/share/doc/git/RelNotes/2.7.0.txt` locally, cross-checked against
`git/git`'s own `Documentation/RelNotes/2.7.0.txt` and `builtin/rev-parse.c`
at the `v2.4.0`/`v2.5.0` tags): `--git-common-dir` genuinely was
introduced in Git 2.5.0 (present in `v2.5.0`'s `builtin/rev-parse.c`,
absent in `v2.4.0`'s) — that half of point 8's claim was correct. But
`git worktree list` and `git remote get-url` — both called unconditionally
by `_detect_worktrees`/`_detect_origin_url` on every single invocation,
not merely in some code path — were **both** first introduced in Git
2.7.0 (January 2016): "`git worktree` learned a `list` subcommand" and
"`git remote` learned `get-url` subcommand", both in the same release
notes file. Point 8 checked only `--git-common-dir`'s own floor and
never checked the other two commands this module also depends on
unconditionally, so it understated the module's real minimum by one
minor version.

`decisions/0063`'s own "Alternatives considered" section rejected "a
dedicated, separate `git --version` detection/parsing step... pre-empt
an old-Git failure ahead of the ordinary stderr-based classification" on
the grounds that "the existing classification already produces an
honest, correctly-attributed `unavailable` outcome for a Git too old to
support `--git-common-dir`" — true for a Git below 2.5 (the initial
`rev-parse --show-toplevel --git-common-dir` call itself fails, already
correctly classified `UNAVAILABLE` by the existing generic-failure
branch), but **not** true for a Git in the 2.5–2.6 range: such a Git
passes the initial `rev-parse` call (since `--git-common-dir` already
works), then fails later at `git worktree list --porcelain` with a raw
"unknown subcommand"-style stderr message that the existing code
classified as generic `PARTIAL` (an "unexpected" enumeration failure),
not as the structurally-expected, version-attributable failure it
actually is — a real gap the rejected alternative would have closed, had
the true floor been known at the time.

## Decision

**`decisions/0063` point 8 is superseded by this ADR.** Neither `0063`'s
nor this ADR's own original text is edited (`CLAUDE.md` §2's append-only
convention, exercised previously at `decisions/0061`). Read `0063` point
8 as historical/incorrect on the specific Git-2.5-floor claim; this ADR's
own decision below is current truth.

**1. Git 2.7.0 is `git_topology.py`'s real, documented minimum version**,
gated by `git worktree list` and `git remote get-url` — both called
unconditionally on every `detect_git_topology` invocation that reaches a
real repository. `--git-common-dir` (Git 2.5) remains necessary but is no
longer sufficient to state as the floor.

**2. The alternative `decisions/0063` rejected — a direct `git --version`
check — is adopted, narrowly.** New evidence (the 2.5–2.6 gap above)
satisfies the bar `0063`'s own rejection implicitly set ("no evidence...
calls for it"): there now is such evidence. The check is a single
`git --version` call (`_detect_git_version`), parsed with one small
regex (`git version (\d+)\.(\d+)`), run once per `detect_git_topology`
invocation, only after a real repository/worktree has already been
confirmed via the existing `rev-parse` call and only before either
2.7-gated command is attempted. A version that parses and is below `(2,
7)` short-circuits immediately to `UNAVAILABLE` with an explicit,
version-naming reason (e.g. "git 2.6 is older than the minimum version
(2.7) required for repository topology detection (git worktree list /
git remote get-url)"). A version that fails to parse (an unusual build,
non-English locale, or any `git --version` failure) never blocks
detection — normal enumeration proceeds and will itself fail honestly
(as `PARTIAL`/`UNAVAILABLE`, per the existing, unmodified failure
handling) if the installed Git genuinely can't service the calls made.

This is deliberately **not** the complex, multi-cause compatibility
machinery a broader "support older Git" effort might build — it is one
cheap, deterministic check against one documented floor, consistent with
this phase's own established preference (`decisions/0063` point 7, bare
repositories) for declaring an unsupported case honestly rather than
building fallback support for it.

**3. This does not change any other `decisions/0063` decision.** The
three-table schema, two-level uncertainty model, introspection-based
migration fix, bare-repository non-support, scheme-aware URL
sanitisation, `.gitmodules` path-safety check, and per-worktree database
isolation are all unaffected and remain exactly as `0063` describes them.

## Alternatives considered

- **Leave the Git 2.5 claim as originally stated, treat the 2.5–2.6 gap
  as accepted risk.** Rejected — a real repository on a genuinely
  plausible, still-encountered Git version (2.6 shipped less than ten
  years before this phase; RHEL/CentOS 7's system Git was 1.8.3, but a
  manually-updated or vendor-backported 2.5/2.6 install is a real,
  non-hypothetical scenario) would receive a raw, unexplained `PARTIAL`
  result with a confusing git-internal error string as its "reason" —
  exactly the dishonest-by-omission outcome this project's own explicit-
  uncertainty discipline exists to prevent.
- **Pattern-match the specific "unknown subcommand"-style stderr text
  from `git worktree list`/`git remote get-url`, the same style already
  used for the bare-repository and not-a-repository cases, instead of a
  version check.** Rejected — unlike `rev-parse`'s bare-repository stderr
  (a single, stable, well-known message across Git versions), an
  "unrecognized subcommand" error's exact wording is not something this
  project verified is stable across the specific old-Git versions or
  locales it would need to match reliably; a direct version comparison
  against a documented floor is simpler, deterministic, and does not
  depend on matching fragile, potentially localized error text.
- **Support Git 2.5–2.6 by finding older equivalents of `worktree list`/
  `remote get-url`.** Rejected outright, per the corrective pass's own
  explicit instruction and this project's own established posture: no
  evidence calls for supporting a Git this old, and doing so would be
  exactly the "complex compatibility fallback" this phase continues to
  decline to build.

## Consequences

- `git_topology.py`'s module docstring, `decisions/0063`'s own
  "Consequences" Git-2.5 claim (left as historical/incorrect, per
  append-only), `architecture/overview.md`, `docs/cli-reference.md`, and
  `planning/phase-76-git-repository-topology.md` are all corrected to
  state Git 2.7, not 2.5.
- One additional `git --version` subprocess call per `detect_git_topology`
  invocation, only after a real repository has already been confirmed —
  negligible cost, consistent with this module's existing per-invocation
  subprocess-call volume.
- A Git in the 2.5–2.6 range now receives a clear, actionable
  `UNAVAILABLE` diagnostic instead of a confusing `PARTIAL` one; a Git
  below 2.5 is unaffected (already correctly `UNAVAILABLE` via the
  pre-existing generic `rev-parse` failure path).
- This correction was found and fixed as part of a narrowly-scoped,
  post-closeout corrective pass on Phase 76 (already marked `done`) — see
  `planning/retros/phase-76-git-repository-topology.md`'s corrective-pass
  addendum for the full circumstances.
