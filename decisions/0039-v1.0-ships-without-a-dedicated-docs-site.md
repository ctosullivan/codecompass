# 0039. v1.0 ships without a dedicated docs site — `README.md` + `docs/*.md` rendered on GitHub only

## Status

Accepted

## Context

Phase 23 (`planning/phase-23-polish-and-pypi-publish.md`) is the release
phase itself, and its Part A scope explicitly calls for "a short written
decision (a new ADR, not a built site) on whether v1.0 ships with a
dedicated docs site (mkdocs/ReadTheDocs/etc.) or relies on `README.md` +
`docs/*.md` rendered directly on GitHub." This question had never been
raised or decided before this phase — earlier phases wrote and maintained
`README.md`, `docs/cli-reference.md`, `docs/config-schema.md`,
`architecture/overview.md`, and `decisions/*.md` under this project's own
same-commit doc-sync discipline (`CLAUDE.md` §2), but nothing until now
asked whether that documentation should also be built into a separate
rendered site (mkdocs, ReadTheDocs, Docusaurus, or similar) as part of the
v1.0 release, versus continuing to rely on GitHub's native Markdown
rendering of the files already there.

The project has no external users yet: this is a first public release,
not a response to observed navigation or discoverability complaints from
real usage. Any docs-site decision made now is necessarily speculative
about what real users will actually need, since there aren't any yet to
ask.

## Decision

**Ship v1.0 without a dedicated docs site.** `README.md` (entry point,
quickstart, feature overview) plus `docs/cli-reference.md` and
`docs/config-schema.md` (detailed reference), `architecture/overview.md`
(system design), and `decisions/*.md` (the full ADR trail) — all already
written, already kept in sync with every phase under `CLAUDE.md` §2's
same-commit discipline, and all natively rendered by GitHub's Markdown
viewer with working relative links, syntax highlighting, and a file
browser — are the complete documentation surface for v1.0. No mkdocs
config, no ReadTheDocs project, no static-site generator, no separate
build/deploy pipeline.

Three reasons this is the right call specifically *now*, not a
permanently-closed question:

1. **The existing docs are already thorough and cross-linked.** This
   isn't a "docs are thin, so a site would help" situation — every
   command has a reference entry, every non-obvious decision has an ADR,
   and the system design has a dedicated overview doc. A docs site's main
   value proposition (organizing otherwise-scattered or shallow docs into
   a navigable structure) is weaker when the source docs are already
   organized and cross-linked via relative Markdown links that GitHub
   already resolves correctly.
2. **A docs site is a second place documentation can drift out of sync.**
   This project's whole documentation discipline (`CLAUDE.md` §2 and §5)
   is built around docs updating in the *same commit* as the code change
   that affects them. A generated site adds a build step between "docs
   file changed" and "site reflects that change" — a gap where staleness
   can hide (a merged PR with correct source Markdown, but a site that
   hasn't rebuilt yet or whose build silently failed) that plain
   GitHub-rendered Markdown doesn't have, since there's no intermediate
   build to go stale.
3. **No real users yet means no real navigation-need data.** A docs
   site's actual value (search, versioned docs, a curated nav sidebar,
   custom theming) is easiest to get right when shaped by how real users
   actually try to navigate the docs and get stuck — none of which exists
   yet for a project about to have its first public release. Building
   navigation infrastructure now would be guessing at a problem that
   hasn't been observed, for an audience that doesn't exist yet.

This is a deferral, not a rejection — revisit once v1.0 has real external
users and their actual navigation friction (if any) is observable, rather
than guessed at now.

## Alternatives considered

- **Ship a minimal mkdocs site at v1.0**, e.g. `mkdocs-material` with the
  existing `docs/*.md` files pulled in mostly as-is, deployed to GitHub
  Pages. Rejected for now: the marginal navigation improvement over
  GitHub's own Markdown rendering (a `docs/` folder with a handful of
  well-linked files is already easy to browse) doesn't clearly outweigh
  taking on a second build pipeline and a second place docs can silently
  drift, for a project with no evidence yet that real users find GitHub's
  rendering insufficient. Revisit if that evidence shows up post-release.
- **Publish to ReadTheDocs specifically** (rather than a self-hosted
  mkdocs/GitHub Pages site). Rejected for the same core reason as the
  mkdocs alternative, plus an additional cost: ReadTheDocs integration
  usually assumes Sphinx-style docs (reStructuredText or a Sphinx
  Markdown extension) or at least a documented build config, which this
  project's plain-Markdown docs aren't currently structured for — adopting
  it would mean restructuring existing, working docs to fit a hosting
  platform's expectations, not just wrapping them.
- **Decide this later, without writing anything down now.** Rejected —
  this is exactly the situation `CLAUDE.md` §2 already anticipates for
  ADRs: "write a new ADR whenever a phase involves a non-obvious tradeoff,
  not only for decisions already known at project start." Leaving the
  question silently unconsidered would mean a future session (or a future
  contributor) has no record that a docs site was ever evaluated and
  deliberately deferred, versus simply never having come up — the two
  look identical without a written decision, and only one of them is
  actually true.

## Consequences

- No docs-site build/deploy step is part of this or any future release
  process unless a later ADR supersedes this one — nothing in CI, no
  GitHub Pages branch, no ReadTheDocs webhook to maintain or that could
  silently break.
- Discoverability for a prospective user depends entirely on `README.md`
  being a good enough entry point and GitHub's own repo browsing/search —
  no site-level full-text search, no versioned-docs switcher across
  releases. Acceptable for a first release with no version history to
  navigate yet; worth revisiting once multiple tagged releases exist and
  a user might need docs for a version they're actually pinned to, rather
  than always reading `main`.
- If a future phase does build a docs site, this ADR is the record of why
  v1.0 shipped without one — that phase should treat this ADR as
  superseded (a new numbered ADR, per `CLAUDE.md` §2's append-only rule),
  not silently contradict it.
- Nothing about this decision blocks or complicates a future docs site —
  the existing `docs/*.md`/`architecture/*.md` files are already plain
  Markdown with working relative links, a reasonable starting point for
  most static-site generators if that day comes.
