# 0024. Context graph stored as a single root-level file, not per-vendor

## Status

Accepted

## Context

Phase 9 (`planning/ROADMAP.md`) introduces a context graph: deterministic
data recording which project source files use which vendors/symbols,
which docs cover which symbols, how Skill routing maps onto vendors, and
how vendors depend on each other (`planning/phase-9a-vendor-presence-graph.md`
onward). Every existing generated artifact in this project is scoped to
one vendor at a time — `vendor/<name>/{CLAUDE.md,DEPTREE.md,FILETREE.md,
deptree.json,filetree.json}` — because every existing generation step
(`sync_vendor`) operates on one vendor independently.

The context graph's data doesn't fit that shape. A `SourceFile → Vendor`
or `SourceFile → Symbol` usage edge (9a/9b) is inherently project-wide: a
single source file can reference several vendors, and a single vendor can
be referenced from many files scattered across the project. `DEPENDS_ON`
edges (9c) and coverage-gap queries ("what's used but undocumented") are
inherently cross-vendor by construction. Storing this data per-vendor
would mean either duplicating a shared source file's usage record across
every vendor directory it touches, or introducing a cross-referencing
scheme none of the existing per-vendor artifacts need.

## Decision

The context graph is stored as a single file, `context-graph.json`, at
the project root — a sibling to `vendor.toml`, not nested under any
`vendor/<name>/` directory. It contains all node and edge types produced
by 9a–9c (`vendors`, `source_files`, `symbols`, `doc_artifacts` nodes;
`uses`, `documents`, `routes_via`, `depends_on` edges) under `nodes`/
`edges` top-level keys, plus a top-level `enrichment` key that is `null`
until Phase 9d's optional LLM layer runs (`decisions/0026`).

No per-vendor *view* files (e.g. a rendered "usage" section appended to
each vendor's `CLAUDE.md`) are generated by this plan. If a future phase
wants a human-readable per-vendor slice, it renders one from
`context-graph.json` rather than depcompass maintaining two sources of
truth for the same data.

## Alternatives considered

- **Per-vendor JSON shards with a root composition index** (e.g. a
  `usage.json` under each `vendor/<name>/`, indexed from the root).
  Rejected — fragments a single source file's usage record across every
  vendor directory it references, and `depends_on`/coverage-gap queries
  would need to read every shard anyway to answer a single question,
  giving no real locality benefit over one file.
- **Embed the graph inside `vendor.toml` itself.** Rejected —
  `VendorConfig` is a small, hand-edited, three-field config file
  (`decisions/0011`); it is not a generated-data target, and mixing
  hand-authored config with a machine-regenerated graph in the same file
  would make diffs and hand-edits both harder to reason about.
- **One graph file per ecosystem.** Rejected — no existing artifact in
  this project is split by ecosystem rather than by vendor or by project,
  and cross-ecosystem queries (e.g. "which vendors, across all
  ecosystems, are unused") would need to read every shard regardless.

## Consequences

- `context-graph.json` becomes a new generated, presumably-committed
  artifact — the same reasoning that keeps `deptree.json`/`filetree.json`
  committed (deterministic, diffable, no regeneration needed just to
  view) applies here for the 9a–9c layer.
- A future Phase 10 (the project-root REPL routing/rollup work this
  graph exists to support) may render vendor-scoped views from this file
  if it needs them — explicitly out of scope for this plan, not
  preemptively built.
- Any future change to swap this for a per-vendor or sharded model is a
  storage-model change and supersedes this ADR with a new one, per
  `CLAUDE.md` §2's append-only convention for `decisions/`.
