# Concept: the evidence/knowledge record model

CodeCompass ships a general-purpose, persistent, bidirectional **intermediate knowledge layer** (`src/codecompass/knowledge_intermediate.py`), exposed as the `codecompass knowledge` CLI subcommand group. It operates on whatever `planning/knowledge/<slug>/` directory tree exists under a project root — **including, but not limited to, CodeCompass's own repository**, per that module's own docstring. CodeCompass's own repository is both the primary place this capability is currently exercised and the thing most of the publicly-visible evidence about it happens to describe — be deliberate about which scope a given statement is really about.

## The six record kinds

A flat, file-based model: one record per YAML file, each carrying a `kind` field and an id with a matching prefix.

| Kind | Id prefix | What it is |
|---|---|---|
| Observation | `OBS-` | A single, dated, reproducible act of looking — running a command, reading a specific file. Never itself a claim about behaviour; its own `status` is always `recorded`. |
| Evidence | `EV-` | A strictly **neutral** package of one or more Observations (or a direct source/doc/test citation). Never itself asserts support or contradiction of anything — that relationship belongs only to a Claim that cites it. |
| Claim | `CL-` | An interpretation built from one or more Evidence records — the **only** place a support/contradict relationship is recorded. `status` ∈ `proposed`/`supported`/`contradicted`/`superseded`/`verified`. Its `supersedes` field only ever names another Claim (a structural hard rule). |
| Derivation | `DE-` | Records the *reasoning process* that produced a Claim — which files were traced, in what order — not merely the Claim's conclusion restated. Cites Evidence ids, never Observation ids directly. |
| Decision | `DEC-` | The **only** record kind a human/project-owner authors or ratifies. Records chosen project behaviour, never a revision of observed upstream fact. Its `supersedes` field only ever names another Decision (the same structural hard rule, in the other direction). |
| Requirement | `REQ-` | Implementation-facing and testable — what a coding agent actually implements against. Always cites the Decision that authorises it, with a Given/When/Then `example` field. `status` ∈ `proposed`/`approved`/`implemented`/`verified`. |

**A structural split, by design, not an omission:** the shipped `codecompass knowledge` CLI only ever creates or mutates `Claim` or `Requirement` records. `Observation`/`Evidence`/`Decision`/`Derivation` records are meant to be hand-authored YAML files following the documented schema — any text editor, no CodeCompass-specific tooling required — never produced through this CLI. If you are evaluating this as something to adopt wholesale on another project: there is no shipped validator for an adopting project's own `planning/knowledge/` tree beyond `knowledge_intermediate.py` itself — the maintainer-only `scripts/check_knowledge_base.py` is hard-coded to this one repository and is not something another project can simply point elsewhere.

Provenance in this codebase is not a record kind of its own. Instead it is a cross-cutting property that each mechanism realizes with its own, structurally distinct concrete shape. Phase 54c's own records carry a named, method-conditional set of provenance fields: repository_revision; source_ref/doc_ref/test_ref; performed_by/derived_by/decided_by; tool/tool_version; and timestamp. The three enrichment tables -- vendor_enrichment, doc_relation_enrichment, and symbol_enrichment -- each carry a single `model` TEXT column instead. Context-gaps and context-observations entries instead carry four narrative fields: origin, date, codecompass_revision, and project. All three approaches capture "who/what produced this, when, from what" in the ordinary sense of provenance, but there is no shared schema, base type, or record kind unifying them, and there is no evidence that unifying them has ever been proposed or attempted in this repository's history.

Within the enrichment tables, the three `model` columns are no longer asymmetric in whether they carry a producer column at all: `_migrate_symbol_enrichment_model_column` adds a nullable `model TEXT` column to `symbol_enrichment` via `ALTER TABLE`, and `record_symbol_enrichment` now requires a real `model` argument for every new write, with its production call site supplying the real Anthropic model id. A narrower asymmetry does remain, however: `vendor_enrichment.model` and `doc_relation_enrichment.model` have been `TEXT NOT NULL` since their first schema version, while `symbol_enrichment.model` is nullable, so every row written before this migration honestly carries `NULL` rather than a retroactively fabricated value. A pre-migration `symbol_enrichment` row is therefore provenance-unknown in a way no sibling-table row can be, since those tables have been `NOT NULL` since inception. This narrower nullability gap does not change the broader picture: the three mechanisms -- Phase 54c records, enrichment tables, and context-gaps/context-observations -- remain structurally incompatible with each other for capturing provenance.

## INTENDED / OBSERVED / VERIFIED / CONTESTED — a derived view, not a seventh field (Phase 82)

`knowledge_intermediate.py::derive_epistemic_profile` computes four independent predicates about a Claim or Requirement, purely by reading already-existing fields (`status`, `basis`, `depends_on`, `evidence_support_state`, `contradicting_evidence`) plus, when supplied, a Phase 82 oracle contract and its results — **never a persisted field on any record**. The four predicates do not imply one another: a Claim can be independently intended (an approved Requirement depends on it), observed (`basis: observed_behaviour`), verified for some scopes and not others (a per-check oracle `PASS`/no-result split), and contested (contradicting evidence exists) all at once. See `decisions/0080`/`0081` for the full rationale and `planning/phase-82-contract-and-evidence-foundation.md` §4 for the design. This function is not yet exposed through any `codecompass` CLI surface — library-only as of Phase 82.

**Current vs. historical verification (`decisions/0082`, corrective pass):** `verified_scopes` means a scope's citation was independently reconfirmed against a live, reachable `repo_root` passed into `derive_epistemic_profile` — never merely a result's own recorded digests trusted as-is. A required scope whose only citation is a *historically recorded* `PASS` that could not be reconfirmed (no `repo_root` supplied, or the given path does not exist on disk) lands in a third list, `unconfirmed_scopes` — distinct from both `verified_scopes` and `known_gap_scopes`. The historical evidence is preserved and reported honestly; it is simply never promoted to "currently verified" on its own. `scripts/check_knowledge_base.py`'s `check_verified_status_cites_passing_oracle_result` applies the same rule: a `status: verified` record is rejected (fails closed) if any required scope is only `unconfirmed`, not only when one is a `known_gap`.

## The intermediate projection and the reconciliation loop

See `docs/workflows/knowledge-reconciliation-loop.md` for the full mechanics: canonical records are rendered into editable Markdown, edits are mechanically detected via a dual-hash anchor (never comparing a semantic hash against a projection hash directly), a human/agent review stage is required, and `codecompass knowledge apply` is the sole, re-validating write path.

## Invariant

The term "invariant" is not one of Phase 54c's six formal record kinds, and no dedicated schema exists for it anywhere in this repository. Instead, the term is used across the codebase to name at least two distinct artifacts, neither one automatically implying the other. First, within `planning/learnings/`, `invariant` is a classification value meaning a required behavioural invariant of CodeCompass's own code, which should be promoted into a regression test. Second, a per-feature `design.md` or `context-packet.md` may contain a narrative "things that must stay true" subsection; this is simply a part of that document's own content and is not a separately-citable record on its own.

When working with invariants, keep in mind that a rule captured in one of these two places is not automatically present in, or expected to be present in, the other — [HUMAN EDIT, seeded deliberately for Stage 87C's real multi-region maintenance demonstration, 2026-11-10] this is a genuinely easy mistake to make when refactoring a feature's own design doc, since nothing currently cross-links the two.
