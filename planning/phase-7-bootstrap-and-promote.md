# Phase 7: Zero-question bootstrap & promote

## Scope

**Covered:**
- `src/depcompass/discovery.py` — filesystem auto-discovery (walking the
  project root for `package.json`, `pyproject.toml`/`requirements.txt`,
  `Cargo.toml`) feeding the existing `discover_npm`/`discover_python`/
  `discover_cargo` parsers; a new merge-write path that appends newly
  discovered dependencies to an existing `vendor.toml` without touching
  already-recorded entries (`decisions/0017`).
- `src/depcompass/cli.py` — bare `depcompass` (no subcommand) wired to
  auto-discover + write `vendor.toml` (or refresh it) + generate trees +
  `index`, with no prompts and no AI calls (`decisions/0017`); new
  `promote <vendor> [--yes]` command (`decisions/0018`).
- `src/depcompass/source_resolution.py` (new) — per-ecosystem repository
  URL resolution: npm/Cargo `repository` field (npm also reads
  `directory`), PyPI `project_urls` key-variant matching, fail-loud on
  PyPI resolution failure (`decisions/0021`).
- `src/depcompass/grounded_description.py` (new, replaces
  `gap_analysis.py`) — retrieval-grounded `FULL`-depth generation:
  fetches from the resolved repository, produces dual-audience
  (technical + conversational) output referencing retrieved source/docs,
  no `context_path` input (`decisions/0019`).
- `src/depcompass/skill.py` (new) — tool-level Skill template + generator
  (`decisions/0020`, wired into `index`); per-vendor Skill generation +
  Cursor `.mdc` export, moved here from being unbuilt Phase-9 scope and
  now triggered by `promote` (`decisions/0013`, `decisions/0018`).
- `src/depcompass/config.py` — `vendor.toml` schema loses `context_path`;
  gains the merge-write path's "don't overwrite existing entries"
  contract.
- `src/depcompass/core.py` — `VendorConfig` loses `context_path`;
  `VendorDigest`'s gap-analysis-shaped fields
  (`conversational_overview`, `gap_analysis_error`, `action_pointer_*`)
  are renamed/adjusted to match `grounded_description`'s output shape
  (exact field names decided during implementation, not fixed here).
- Tests: `tests/test_discovery.py` (bootstrap/refresh idempotency),
  `tests/test_source_resolution.py` (new), `tests/test_grounded_
  description.py` (new, replaces `tests/test_gap_analysis.py`),
  `tests/test_skill.py` (new), `tests/test_cli.py` (bare invocation,
  `promote`), `tests/test_config.py` (merge-write, schema change).
- Same-commit doc updates: `docs/cli-reference.md`, `README.md`'s "Quick
  example," `architecture/overview.md` ("Retrofitting to existing
  projects," "Cost model," "Gap analysis" → grounded description),
  `planning/ROADMAP.md`, `planning/CONTEXT.md`, `CHANGELOG.md`.

**Explicitly deferred:**
- Batch promotion (`promote --all` or similar) — `decisions/0018`
  defers this; single-vendor only for now.
- `context_path`-biased grounded description (using an optional
  project-context input to bias the description) — `decisions/0019`
  defers this as a future refinement.
- The concept/spec-skill extension described in the originating design
  doc (a skill scoped to a file-format spec rather than a vendor) — not
  started, noted only so it isn't rediscovered from scratch.
- A manual repository-URL override in `vendor.toml` for the PyPI
  fail-loud case (`decisions/0021`) — not introduced until real usage
  shows it's needed.
- Any live validation of the Cargo adapter beyond what already exists
  (`decisions/0014`'s accepted gap — still blocked on no local Rust
  toolchain, unrelated to this phase).

## Design decisions

- **Two distinct "get the source" mechanisms stay distinct.** The
  existing `vendor/<name>/src/` snapshot (`decisions/0004`,
  `decisions/0010` — a copy of the *locally installed* package, gitignored,
  regenerated by `sync`) is retained for what it already does: a stable
  reference for the deterministic `FILETREE`/`DEPTREE` output, unaffected
  by this phase. `source_resolution.py` (`decisions/0021`) resolves the
  *upstream repository URL* — a separate concern, needed because a
  locally-installed package (an npm tarball, a PyPI wheel/sdist, a
  crates.io package) is a build artifact that frequently excludes README/
  docs content present in the actual repository. **Open implementation
  question, not resolved by this plan:** whether `grounded_description`'s
  retrieval should populate `vendor/<name>/src/` itself (sourced from the
  resolved repository instead of the local install, once a vendor is
  promoted) or use a separate location — needs a concrete answer before
  implementation starts, since it changes what `decisions/0004`'s
  existing snapshot represents for `FULL` vendors.
- **Retrieval scope for grounded generation — proposed default, to be
  confirmed before implementation (per `CLAUDE.md` §1: an unsettled
  assumption surfaced while writing this plan).** README (repository
  root, plus a `docs/`/`doc/` folder if present) plus the package's
  top-level entry-point source file/module, capped at roughly 50KB of
  raw text before chunking, chunked to fit within a single Haiku call
  where possible. Forced tool-use schema, dual-audience output
  (`decisions/0012`), with each claim tagged to the source file it came
  from. Reuses `gap_analysis.py`'s `_call_anthropic` seam (renamed into
  `grounded_description.py`) and `decisions/0016`'s never-call-the-live-
  API testing constraint.
- **Per-vendor Skill generation inside `promote` carries forward
  `decisions/0013`'s unfinished requirements**, since that work was
  originally scoped to a standalone Phase 9 that this phase now absorbs:
  trigger-description length as a tuning knob (specificity over
  verbosity, not maximized for recall); `FILETREE.md`/`DEPTREE.md`
  bundled as `references/` inside the Skill folder for progressive
  disclosure; a trigger-accuracy evaluation step (a small battery of test
  questions per promoted vendor, checked against whether the
  corresponding Skill actually loads); the REPL's future escalation path
  (Phase 8/9, not this phase) will point at the Skill folder this phase
  produces.
- **`init --scan`'s existing strict contract (errors if `vendor.toml`
  exists) is preserved exactly** — only the new bare-invocation path gets
  idempotent-refresh semantics, so scripted/CI callers of `--scan` see no
  behavior change.
- **`promote`'s cost disclosure and confirmation gate** follows the same
  pattern `sync --budget` already established for cost-awareness
  (Phase 5) — printed before any API call, with a `--yes` flag for
  non-interactive use (CI, scripted promotion of a specific known
  vendor) mirroring how `--strict`/`--fix` are flags on `check` rather
  than prompts.
- **ROADMAP renumbering** (see `planning/ROADMAP.md`): this phase absorbs
  the prior Phase 9 (Agent Skills + Cursor export) and Phase 10 (`init`
  bulk-discovery refinement) rows entirely; both are removed as separate
  rows rather than marked "done elsewhere," since their scope is now
  fully contained here.

## Verification

- `pytest` — full suite passes; no test makes a real Anthropic API call
  or a real network/subprocess call for source resolution (fixture-mocked
  per the pattern `decisions/0014`/`0016` already established).
- `ruff check .` — clean, including all new modules.
- Bare `depcompass` on a project with no `vendor.toml`: writes one at
  `SURFACE` for every discovered manifest dependency, generates trees,
  updates root `CLAUDE.md`, makes no AI call, requires no input.
- Bare `depcompass` run twice in a row on the same project: second run is
  a no-op with respect to already-recorded vendors (no duplicate
  entries, no depth changes), only picks up genuinely new dependencies
  if the manifest changed between runs.
- `promote <vendor>` on a `SURFACE` vendor: prints cost disclosure,
  requires confirmation (or `--yes`), sets `depth = FULL`, produces
  grounded content + Skill + `.mdc`, `index` reflects the change.
- `promote <vendor>` on an already-`FULL` vendor: same disclosure/
  confirmation, regenerates in place, doesn't error.
- `promote` against a PyPI vendor with no resolvable `project_urls`
  entry: fails loudly for that vendor, `vendor.toml` unchanged
  (`decisions/0021`).
- `promote` against an npm vendor with a monorepo `directory` field:
  retrieval is scoped to the correct subdirectory, not the whole repo.
- `promote` against a Cargo vendor: exercised via fixture-mocked source
  resolution and generation (real `cargo` output remains unverified per
  `decisions/0014`'s accepted, unrelated gap).
- A hand-inspected `SKILL.md` for a promoted vendor and the tool-level
  `SKILL.md`: both readable, tool-level one present even with zero `FULL`
  vendors.

## Status

done — both open questions flagged above were resolved before
implementation began (per `CLAUDE.md` §1): retrieval scope proceeds
exactly as proposed (README + docs folder + entry-point file, ~50KB cap,
confirmed via `AskUserQuestion`); `vendor/<name>/src/` is reused,
sourced from the resolved repository, with a fallback to the old
local-install copy if source resolution fails (implemented in
`sync_vendor` as a nested try/except, not a flat one — cloning success
followed by generation failure keeps the real clone rather than
discarding it for the fallback).

All verification steps passed: `pytest` reports 207 passed, 1 skipped
(the Cargo live smoke test, unchanged since Phase 2) — up from 162 at
the end of Phase 6; `ruff check .` is clean. Bare `depcompass` and its
idempotent refresh were manually verified end-to-end in a scratch
directory (auto-discovery, `vendor.toml` creation, tree/routing-table/
tool-Skill generation, and a second no-op run). Source resolution and
cloning were manually verified against a real repository — `pytest`'s
own, resolved via its real PyPI `Project-URL` metadata (`Source,
https://github.com/pytest-dev/pytest`) and shallow-cloned with real
`git` — confirming `repository_url()`, `resolve_and_clone`, and
`_gather_material` all work against live, non-fixture data. The AI call
itself (`generate_grounded_description`) was **not** exercised against
the live Anthropic API in this session — consistent with
`decisions/0016`'s existing posture (Phase 5 accepted the same gap for
`gap_analysis.py`) and this project's general caution around agents
autonomously incurring real API spend; a human should run
`depcompass promote <vendor>` against a real vendor with a real
`ANTHROPIC_API_KEY` at least once before trusting output quality.

One item from Design decisions was **not** implemented, and is carried
forward rather than silently dropped: the trigger-accuracy evaluation
step for per-vendor Skills (a battery of test questions checked against
whether the Skill actually loads) — no such harness exists yet. Skill
generation itself (description built from a condensed conversational
overview, `references/` bundling) is implemented and tested.

Two Cargo-specific items remain unverified, both pre-existing accepted
gaps (`decisions/0014`) rather than new Phase 7 gaps: `CargoAdapter.
repository_url()` is only fixture-tested, and `promote`'s end-to-end
flow against a real Cargo vendor is untested — no Rust toolchain is
available in this environment.
