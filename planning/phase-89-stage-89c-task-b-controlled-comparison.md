## 3. Task B implementation scope

Reproduced and pinned, so both arms receive byte-identical task
framing (§4's equivalence requirement) and the acceptance test (§6) can
call a single, stable public interface regardless of which arm
produces it.

**Honest framing, stated to both arms verbatim (not softened for
either)**: "This is a controlled-comparison exercise, not a live
Ledgerkit maintainer request. Implement a real, working feature
exactly as specified below; your work will be evaluated on genuine
correctness and quality, not on the fact that the task was
synthetically selected."

**Exact required signature** (pinned now, not left to either arm to
invent — a pinned signature is required so the acceptance test, authored
before either arm starts, can call it deterministically; this is the
one piece of "contract design" this plan performs, mirroring Phase 78
Stage 3's own "one shared implementation contract... not invented fresh
by whichever agent happens to implement it," §5.3.3 step 1 of that
plan):

```python
@staticmethod
def with_combined_section(
    name: str, *sections: ReportSection, label: str | None = None,
) -> ReportSection:
    """Returns a single new ReportSection whose `accounts` is the
    union of every given section's own `accounts` patterns (and
    `exclude`, unioned the same way), for a caller who wants one
    combined subtotal spanning what were previously separate
    sections. Does not mutate any input section."""
```

Required behaviour, stated identically to both arms as the task's own
acceptance surface (not left ambiguous — an ambiguous edge case left to
each arm's own interpretation would itself become an uncontrolled
variable):

- Given two or more sections, returns one new `ReportSection` named
  `name` (or `label` if given, else defaulting the same way
  `ReportSection.label` already defaults — `f"Total {name}"` is the
  existing convention, confirmed in `ledgerkit/models.py`'s own
  `ReportSection` docstring).
- `accounts` is the union of all input sections' own `accounts`
  tuples; `exclude` is the union of all input sections' own `exclude`
  tuples. Order is not asserted by the acceptance test (a set-equality
  check, never a tuple-equality check, per §6).
- All input sections must share the same `invert` value and the same
  `depth` value; if they do not, raise `ValueError` (combining an
  inverted and non-inverted section, or two different depth caps, has
  no single obvious semantic — the task explicitly requires failing
  closed rather than silently picking one side).
- Called with zero sections: raise `ValueError` (never return a
  section with empty `accounts`, which would silently match nothing).
- Called with one section: may return an equivalent section (not
  required either way by the acceptance test; implementers may choose
  either, the test does not probe this edge).
- Must not mutate any input `ReportSection` (they are frozen
  dataclasses already, so this constraint is closer to "if you work
  around immutability, don't" than a real design choice — included for
  completeness, not because it is likely to be violated).
- The combined section, once constructed, is used **exactly like any
  other `ReportSection`** — passed into a `ReportSpec`'s own `sections`
  tuple and evaluated by the existing, unmodified `balance_from_spec`.
  **This constructor itself performs no aggregation and calls no
  posting-matching logic** — it only merges the two declarative
  pattern tuples. (This is the single most important sentence in this
  task specification: it is the one hint the task framing gives both
  arms equally about where the correct implementation boundary lies,
  deliberately included because withholding it would turn the task
  into "figure out `balance_from_spec`'s own matching code is reusable
  at all," a different and harder question than the one this
  pre-registration's own §3 describes testing.)

# tests/test_combined_section_acceptance.py  -- new, added ONLY to a
# disposable, post-arm-dispatch verification clone (never to either
# arm's own ledgerkit-control/ledgerkit-treatment during their own
# dispatch -- those clones contain ONLY each arm's own code; this test

import unittest
from decimal import Decimal

from ledgerkit.loader import load_journal
from ledgerkit.models import ReportSection, ReportSpec
from ledgerkit.reports import balance_from_spec
from tests.test_reports import FILTERED_JOURNAL


class TestCombinedSectionAcceptance(unittest.TestCase):
    def setUp(self):
        self.journal = load_journal(FILTERED_JOURNAL)

    def test_overlapping_patterns_across_combined_sections_counted_once(self):
        # "groceries" alone matches only expenses:food:groceries (150.00).
        # "food" alone matches BOTH expenses:food:groceries (150.00) AND
        # expenses:food:coffee (9.00) -- already-established behaviour
        # (CL-BFS-004). The correct implementation unions the two
        # sections' own account patterns into ONE new ReportSection and
        # relies entirely on balance_from_spec's existing per-posting
        # OR-gate to avoid double-counting groceries (159: groceries
        # once, coffee once) -- it needs no deduplication logic of its
        # own. An implementation that instead distrusts the existing
        # gate and adds its own defensive deduplication (e.g. filtering
        # or excluding a pattern it believes is now "redundant" because
        # another pattern in the combined set already matches the same
        # posting) risks silently dropping a pattern that is NOT
        # actually redundant for every posting -- correctness review
        # independently confirmed this test discriminates exactly that
        # realistic failure mode (an incorrect, unneeded dedup/exclude
        # attempt), not only the specific wrong-arithmetic scenario a
        # much earlier draft of this comment described (which turned
        # out to be structurally unreachable given this function's own
        # pinned `-> ReportSection` return type, which never itself
        # computes a subtotal at all -- flagged and corrected by
        # independent plan review, `planning/retros/
        # _review-phase89-stage89c-plan.md`).
        groceries = ReportSection("Groceries", accounts=("groceries",))
        food = ReportSection("Food", accounts=("food",))
        combined = ReportSpec.with_combined_section("Groceries and Food", groceries, food)
        self.assertEqual(set(combined.accounts), {"groceries", "food"})
        spec = ReportSpec(name="Combined check", sections=(combined,))
        [result] = balance_from_spec(self.journal, spec)
        self.assertEqual(result.subtotal, Decimal("159.00"))

    def test_non_overlapping_patterns_sum_correctly(self):
        housing = ReportSection("Housing", accounts=("housing",))
        groceries = ReportSection("Groceries", accounts=("groceries",))
        combined = ReportSpec.with_combined_section("Housing and Groceries", housing, groceries)
        spec = ReportSpec(name="Combined check", sections=(combined,))
        [result] = balance_from_spec(self.journal, spec)
        self.assertEqual(result.subtotal, Decimal("1350.00"))  # 1200 + 150

    def test_three_or_more_sections_combine_correctly(self):
        housing = ReportSection("Housing", accounts=("housing",))
        groceries = ReportSection("Groceries", accounts=("groceries",))
        food = ReportSection("Food", accounts=("food",))
        combined = ReportSpec.with_combined_section("All", housing, groceries, food)
        spec = ReportSpec(name="Combined check", sections=(combined,))
        [result] = balance_from_spec(self.journal, spec)
        self.assertEqual(result.subtotal, Decimal("1359.00"))  # 1200+150+9, groceries once

    def test_zero_sections_raises(self):
        with self.assertRaises(ValueError):
            ReportSpec.with_combined_section("Empty")

    def test_conflicting_invert_raises(self):
        income = ReportSection("Income", accounts=("income",), invert=True)
        expenses = ReportSection("Expenses", accounts=("expenses",), invert=False)
        with self.assertRaises(ValueError):
            ReportSpec.with_combined_section("Mixed", income, expenses)

    def test_does_not_mutate_input_sections(self):
        groceries = ReportSection("Groceries", accounts=("groceries",))
        food = ReportSection("Food", accounts=("food",))
        before = (groceries, food)
        ReportSpec.with_combined_section("X", groceries, food)
        self.assertEqual((groceries, food), before)

    def test_unrelated_existing_report_behaviour_unaffected(self):
        # Same assertion test_multi_section_correct_values already
        # makes -- confirms this new constructor's own presence in the
        # module has not changed any pre-existing behaviour.
        spec = ReportSpec(
            name="Income Statement",
            sections=(
                ReportSection("Income", accounts=("income",), invert=True),
                ReportSection("Expenses", accounts=("expenses",)),
            ),
        )
        income_result, expense_result = balance_from_spec(self.journal, spec)
        self.assertEqual(income_result.subtotal, Decimal("6000.00"))
        self.assertEqual(expense_result.subtotal, Decimal("1359.00"))

    # --- Added by the second independent dispatch ("Phase 89C Plan
    # Corrections and Independent Re-Review", §6): the original seven
    # tests above left three behaviours §3 explicitly requires
    # untested -- exclude-pattern union, depth-conflict rejection, and
    # label override/default handling. Each new test below was verified
    # this amendment session against both a correct reference
    # implementation (all eleven tests pass) and, for the exclude-union
    # test specifically, a plausible incorrect one (an implementation
    # that unions `accounts` but forgets to union `exclude` at all) --
    # confirmed to fail *exactly* `test_union_of_exclude_patterns` and
    # no other test, i.e. a genuinely discriminating addition, not a
    # restatement of an existing assertion.

    def test_union_of_exclude_patterns(self):
        # section_a excludes nothing; section_b excludes "coffee". The
        # combined section's own exclude must be the UNION, not just one
        # side's -- an implementation that drops or only keeps one
        # section's own exclude set would silently include the coffee
        # posting it should not.
        section_a = ReportSection("Groceries only", accounts=("groceries",))
        section_b = ReportSection("Food minus coffee", accounts=("food",), exclude=("coffee",))
        combined = ReportSpec.with_combined_section("Combined", section_a, section_b)
        self.assertEqual(set(combined.accounts), {"groceries", "food"})
        self.assertEqual(set(combined.exclude), {"coffee"})
        spec = ReportSpec(name="Exclude union check", sections=(combined,))
        [result] = balance_from_spec(self.journal, spec)
        # groceries (150.00) matches accounts, not excluded. coffee (9.00)
        # matches the "food" account pattern but IS excluded by "coffee".
        self.assertEqual(result.subtotal, Decimal("150.00"))
        self.assertNotIn("expenses:food:coffee", result.rows)

    def test_conflicting_depth_raises(self):
        shallow = ReportSection("Shallow", accounts=("expenses",), depth=1)
        deep = ReportSection("Deep", accounts=("expenses",), depth=2)
        with self.assertRaises(ValueError):
            ReportSpec.with_combined_section("Mixed depth", shallow, deep)

    def test_label_override_used(self):
        groceries = ReportSection("Groceries", accounts=("groceries",))
        food = ReportSection("Food", accounts=("food",))
        combined = ReportSpec.with_combined_section(
            "Groceries and Food", groceries, food, label="Food Spend",
        )
        self.assertEqual(combined.label, "Food Spend")

    def test_default_label_omitted_matches_ordinary_section_convention(self):
        # ReportSection's own default is label=None (the f"Total {name}"
        # convention documented in its docstring is resolved by a future
        # renderer, never stored on the section itself -- confirmed by
        # direct inspection: no reference to `.label` exists anywhere in
        # ledgerkit/*.py today). with_combined_section must leave the
        # same None default when no override is given, never inventing
        # its own eager resolution no ordinary ReportSection performs.
        groceries = ReportSection("Groceries", accounts=("groceries",))
        food = ReportSection("Food", accounts=("food",))
        combined = ReportSpec.with_combined_section("Groceries and Food", groceries, food)
        self.assertIsNone(combined.label)
        ordinary = ReportSection("Groceries and Food", accounts=("groceries", "food"))
        self.assertEqual(combined.label, ordinary.label)

## 8. Blinded independent evaluation methodology

1. Run §6's verification sequence for **both** arms (separately,
   against separately-forked `ledgerkit-verify-control`/
   `ledgerkit-verify-treatment`), recording each arm's own acceptance-
   test outcome (per sub-test, plus the one durable `OracleResult` for
   the primary scope) and full-suite regression result, **before**
   dispatching the `context-evaluator` — the evaluator's own job is
   context quality, not re-deriving whether the code happens to pass;
   both facts are reported together but produced independently (§9).
2. **Allocation-blinded presentation (hardened, second independent
   dispatch, "Phase 89C Plan Corrections and Independent Re-Review"):
   an earlier draft supplied filenames/paths containing the literal
   strings "control"/"treatment" to the evaluator (`control-packet.json`,
   `ledgerkit-verify-control`, `control-report.md`, etc.) — this reveals
   allocation despite the surrounding text calling the comparison
   "blind."** Before dispatching the evaluator, the verifier copies
   each arm's own artifacts into a neutral, randomly-assigned pair of
   directories/filenames (`<scratch>/draft-1/`, `<scratch>/draft-2/`,
   re-randomised per run — not always the same arm as "Draft 1"):
   `draft-N-packet.json`, `draft-N-report.md`, `draft-N-verify/` (a copy
   of that arm's own `ledgerkit-verify-*` clone). The allocation key
   (which draft number is actually control vs. treatment) is written to
   a separate file the evaluator is never given, and is not consulted
   again until after the evaluator's own verdict is received. Dispatch
   a **fresh** `context-evaluator` (never a `fork`, never given the
   control/treatment labels) with only the neutral `draft-1`/`draft-2`
   material — order of which real arm becomes "Draft 1" is randomised
   per run. Matches the already-proven blind-comparison convention
   (`planning/retros/phase-87-stage-87c-knowledge-compiled-
   documentation.md` §4/§S.7), now applied to every artifact path the
   evaluator sees, not only its own framing sentence.
3. **Acknowledged, explicit limitation on blinding**: the Evidence
   content itself may reveal which snapshot is more recently reconciled
   (e.g. `EV-BALANCEFROMS-004` only exists in one draft's own packet) —
   this is **substantive Evidence the evaluator must see to do its own
   job** (per `context-quality-evaluation.md` §3's own accuracy/
   relevance/completeness criteria), never concealed merely to preserve
   blinding. This plan describes the procedure as **allocation-blinded
   where practically achievable** (filenames, paths, directory
   structure, framing language), not perfectly blinded — the content
   itself is read on its own merits, same as a real developer would.
4. The evaluator's own instructions (beyond its own standing agent
   definition): inspect the real Ledgerkit source/tests directly to
   establish ground truth (never trusting either draft's own
   self-report); confirm the two packet files' own diff matches
   exactly what §5.4 already established (re-derive this itself, not
   copy this plan's own claim); evaluate each draft's own context
   packet (where one exists) for accuracy/relevance/completeness/
   freshness/grounding/noise/trustworthiness per `context-quality-
   evaluation.md` §3; produce one PASS/PASS WITH GAPS/FAIL verdict and
   one LOW/MODERATE/HIGH context-advantage rating **per draft**;
   explicitly compare the two drafts' own development decisions and
   stated justification for the dedup question (§3); explicitly flag
   any redundant or incorrect deduplication logic found in either
   draft's own code; explicitly apply the `L-027` equal-access check
   (§1) using both arms' own observable research traces (§7.4);
   explicitly name any confound, contamination, or internal
   disagreement it notices; and explicitly answer, separately for each
   draft, "Would this have misled the implementing agent? yes/no/
   partially."
5. **The evaluator reports a negative or inconclusive result exactly as
   found** — no reinterpretation, no "but it would probably help on a
   harder task" narrative substitution (dispatch's own explicit
   instruction, §9 below enforces this at the reporting-schema level
   too).
6. A **separate** `release-phase-auditor` dispatch (never the
   evaluator, never the lead) verifies, after the evaluator's own
   report exists: that this exact plan's own pinned procedure (§4-§8)
   was actually followed (fork-then-dispatch order, read-scope
   statements present verbatim in both dispatch prompts, both prompts
   using the identical symmetric packet-framing sentence from §4.2, the
   acceptance test file unmodified from this plan's own §6 text, the
   evaluator genuinely blinded) — a **procedural-fidelity** audit,
   distinct from the evaluator's own content judgment. This same
   dispatch additionally **audits every evaluator-visible artifact and
   instruction for accidental allocation disclosure** (dispatch's own
   explicit requirement, item 7 above): greps the neutral `draft-1`/
   `draft-2` material and the evaluator's own dispatch prompt for the
   literal strings `control`/`treatment` (case-insensitive) and for any
   file path, clone name, or filename that leaked unredacted from §4.2's
   own internal naming — any hit is reported as a blinding-violation
   finding, not silently excluded, and voids that run's own blinding
   claim (§10's own failure-handling path).

## 10. Failure, timeout, retry, and inconclusive-result treatment

- **Either arm's dispatch errors or times out before producing a
  complete implementation**: record as a failed trial for that arm,
  report Outcome 1 as "not completed" for that arm, and stop — do not
  substitute a different task or re-roll with a different prompt
  hoping for a cleaner result. A single re-dispatch of the **same**
  prompt against a **fresh** fork of the same frozen clone is
  permitted once per arm (transient infrastructure failure only, e.g.
  a tool-call error unrelated to the task itself); a second failure is
  reported as such, not retried again.
- **§5.4's contamination check fails** (packets differ outside the
  four-category allowlist, or `consistency.reasons` does not actually
  diverge for `CL-BFS-004`): stop before dispatching either arm. This is
  an experimental-validity blocker (§1's own instruction), not something
  to patch by hand. Fix the packet-generation call (candidate causes, in
  order of likelihood established by this amendment's own reproduction:
  (1) a pristine, untouched reference checkout is being used instead of
  §5.2's single, shared, test-containing one — the newly-cited
  Evidence's `OracleResult` then evaluates `INVALID` against it, keeping
  `reasons` at `"3 required scope(s)…"` in *both* packets, which a
  naive diff would wrongly read as "clean" rather than "broken"; (2)
  §5.3's two calls did not run against different project roots — check
  the `cmp` step first; (3) the post-reconciliation snapshot (§5.2) was
  built incorrectly, or applied to the wrong copy), re-run §5.4, and
  only proceed once clean.
- **§7.7's boundary check finds a read-scope violation** for either
  arm: report it in Outcome 2 as a procedural-fidelity failure. If the
  violation plausibly gave one arm decisive information the other
  could not have obtained (e.g. a read of the other arm's own clone,
  or of `planning/reference-projects/ledgerkit/`'s own prior findings),
  the trial's own Outcome 3 is **void for this run**, not merely
  footnoted — re-run from §4.2 with a corrected isolation setup, never
  reinterpret the tainted run's own result as if the violation hadn't
  happened.
- **The `context-evaluator` itself disagrees with its own earlier
  assessment on a re-read, or two independent evaluator dispatches
  (if ever run) disagree with each other**: report both verdicts
  honestly, do not average or silently pick the more favourable one;
  this is itself a material finding about the evaluation's own
  reliability on this task, reported in Outcome 2.
- **Acceptance test itself is found to have a bug** (discovered only
  after dispatching, e.g. a fixture amount that does not match the
  real pinned journal): stop, fix the test under this plan's own §6
  text (an amendment to this committed plan file, following this
  project's own ADR-adjacent amendment convention — append, do not
  silently edit history), and **re-dispatch both arms fresh** against
  the corrected test — never apply a fixed test retroactively to only
  one arm's own already-collected result.
- **Tie** (acceptance test agrees for both arms AND evaluator verdict
  identical AND rating identical): report plainly as Outcome 3 = GATE
  NOT MET. Do not search for a tie-breaking metric among §9's own
  exploratory numbers to manufacture a different conclusion (the
  dispatch's own explicit prohibition).
