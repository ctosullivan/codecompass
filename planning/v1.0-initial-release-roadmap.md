# Path to v1.0 — initial release

## Purpose

MVP (v0.2) is `done` (phases 0-19, all shipped). This document lays out
what still needs to happen before cutting an actual `v1.0` tag and
publishing to PyPI — the first release meant for real external users, not
just this project's own dogfooding. It is the roadmap-level umbrella; each
phase below still gets its own `planning/phase-N-<name>.md` per `CLAUDE.md`
§1 before implementation starts (phase 20's already exists; phases 21 and
22 are written alongside this document; 23-25 are not written yet).

Two things are folded into this pass together, at the user's explicit
request:

1. The already-known, already-planned bug fix (Phase 20 — routing
   table/tool Skill/`undo` freshness).
2. A **new feature**: the context graph currently recognizes edges between
   a vendor's own generated docs and symbols (`documents_edges`), between
   Skills and vendors/source files (`skill_mentions_edges`), and between
   vendors (`depends_on_edges`) — but nothing connects a *project's own*
   specification/planning documentation (its README, `docs/`,
   `architecture/`, `decisions/`, etc.) to the dependencies and skills that
   actually support what that documentation describes. That three-way web
   — spec docs, dependency docs, custom skills — is new scope, split into
   a mechanical-detection phase (21) and an AI-enrichment phase (22), for
   the same reason the original v0.2 rework split usage-detection from
   enrichment: mechanical detection is free and deterministic, AI
   enrichment costs money and should only ever run over candidates
   mechanical detection has already proven are related.

## Why this order

```
20  Refresh generated artifacts after enrichment   (bug fix, already planned)
21  Spec-doc detection & relationship graph          (new, mechanical)
22  AI-enriched cross-artifact relationships          (new, paid AI call)
23  Polish: PyPI publish, examples, docs site         (the release itself)
────────────────────────────  v1.0 tag  ────────────────────────────
24  Project-root routing/rollup                       (post-1.0)
25  MCP server                                        (post-1.0)
```

**Phases 20-22 before 23** because Phase 23 *is* the release — cutting a
tag and publishing to PyPI with a known, reproduced correctness bug (20)
or with the newly-requested relationship-graph feature still missing (21,
22) would mean re-releasing almost immediately after. All three are
scoped, bounded, and don't depend on anything not already built.

**Routing/rollup (24) and MCP (25) pushed past the release**, reordered
from their current Post-MVP table position (21, 23) where they sat ahead
of "Polish." This is a deliberate change from the existing `ROADMAP.md`
ordering, flagged here rather than made silently:

- Routing/rollup enhances `chat <vendor>`'s REPL — a subcommand Phase 19
  already explicitly demoted to "secondary, unchanged" (`decisions/0034`).
  `/discovery` and the generated Skills are the primary interface now.
  Shipping v1.0 without a fancier chat-routing layer doesn't leave the
  primary interface unfinished.
- MCP is a new integration surface (a different client entirely — not
  Claude Code, not a terminal REPL) that no existing v1.0 functionality
  depends on. It's natural v1.1+ material once real usage of the CLI/Skill
  surface exists to inform what an MCP server should actually expose.

Both stay on the roadmap, just after the release line — see `planning/
ROADMAP.md`'s Post-MVP table. **This reordering is a proposal, not a
locked decision** — flag it back if routing/rollup or MCP should block
v1.0 instead; nothing about phases 20-23 depends on the answer, so
implementation can start on 20 immediately regardless of how that's
resolved.

## What "spec docs" means (new concept, Phase 21)

Not a new file format or a user-authored config — a *classification* of
files codecompass already has read access to but has never treated as a
graph node. A "spec doc" is human-authored project documentation
describing what the software is, does, or should do, as distinct from:

- **Dependency docs** — codecompass's own generated `vendor/<name>/
  CLAUDE.md`/`OVERVIEW.md` (`origin='codecompass_vendor'`, already in the
  graph).
- **Custom skills** — `.claude/skills/**/SKILL.md` and `.cursor/rules/
  *.mdc`, both codecompass's own and third-party (already scanned by
  `skill_scan.py`, Phase 12).

Detected by convention (default globs — `README.md`, `docs/**/*.md`,
`architecture/**/*.md`, `decisions/**/*.md`, `spec/**/*.md`,
`specs/**/*.md`, `*.spec.md`), scoped to whatever the consuming project
actually has on disk, same "sensible default, no new config surface until
real projects prove the default wrong" posture this project already uses
for `enrichment.py`'s batch size and `usage.py`'s prune-dir set. Full
detection rules and exclusions are in Phase 21's own plan file.

## Phase summaries

- **Phase 20** — `planning/phase-20-refresh-generated-artifacts-after-
  enrichment.md` (already exists, unimplemented). No changes made here.
- **Phase 21** — `planning/phase-21-spec-doc-detection-and-relationship-
  graph.md` (new, written alongside this document). Mechanical-only:
  detects spec docs, links them to vendors/dependency-docs/skills via the
  same word-boundary presence heuristic `doc_mapping.py`/`skill_scan.py`
  already use elsewhere. No AI call, no cost.
- **Phase 22** — `planning/phase-22-ai-enriched-cross-artifact-
  relationships.md` (new, written alongside this document). Takes Phase
  21's mechanically-detected edges as its *only* candidate pool (mirrors
  this project's existing "usage-proven, not manually toggled" enrichment
  gating, `decisions/0031`/`0033`, generalized from vendors to
  relationships) and asks a batched Haiku call to summarize each
  relationship in a sentence or two. Folded into the existing disclosed
  Phase B cost/consent flow — one prompt, not a second one. Written only
  to the graph; never edits a spec doc's own file.
- **Phase 23** *(renumbered from the current Post-MVP table's Phase 22)* —
  Polish: PyPI publish as `codecompass`, examples, docs site evaluation.
  Not written in detail yet.
