## Ground truth I independently re-derived (Part 1)

Read directly, not from either report: `hledger-lib/Hledger/Data/Ledger.hs`
(`ledgerFromJournal`), `hledger/Hledger/Cli/Commands/Stats.hs` (`stats`,
`showLedgerStats`), `hledger-lib/Hledger/Reports/{MultiBalanceReport,
PostingsReport,EntriesReport}.hs`, `hledger/Hledger/Cli/Commands/Accounts.hs`,
`hledger/Hledger/Cli.hs` (`replaceNumericFlags`).

Confirmed: the behaviour is **not uniform**. `balance`/`register`(no
interval)/`accounts` strip depth from posting *selection*
(`filterQuery (not . queryIsDepth)`) and reapply it only as a
display-name clip (`clipOrEllipsifyAccountName`/`clipAccountName`);
`balance` additionally rolls excluded-depth balances up into the
depth-limit row (`markAccountBoring`'s `bdincludingsubs` at the
boundary); `register`, absent a report interval, never merges rows
(confirmed by the module's own embedded test,
`(Depth 2, samplejournal) \`gives\` 13` — same count as no depth limit);
`print` is fully depth-blind (`EntriesReport.hs` strips the term and
never reconsults it); `accounts` clips+dedupes without ever excluding.
`stats` is the genuine exception: `ledgerFromJournal` builds the account
tree from the depth-*unfiltered* postings but also produces `j''`, a
second, depth-*excluded* journal (`filterJournalPostings depthq j'`),
and `Stats.hs`'s own `l = ledgerFromJournal q j` (using the **full**,
depth-included query) feeds `showLedgerStats`, which reads `ts` (the
transaction list) from that same depth-excluded journal.

One nuance neither report fully carries into scope-general language:
**`register` does aggregate when a report interval is given** —
`summarisePostingsInDateSpan` (`PostingsReport.hs:232-251`) rolls up
excluded-depth balances the same way `balance` does
(`bdincludingsubs` when `accountNameLevel a' >= mdepth`). Treatment's
report states this explicitly with the correct citation; baseline's
report states register's behaviour as an unqualified "no aggregation,
no exclusion," which is only true in the (unstated) no-interval case.

**The single most load-bearing check** (independently constructed and
run, not taken from either report): does `stats`'s "Commodities" count
draw from the *same* depth-excluded posting set as "Accounts"? Read
`Stats.hs`'s `showLedgerStats`: `ts = ... jtxns j` (where `j = ljournal
l`, the depth-excluded journal), then **both** `as = nub . map paccount
. concatMap tpostings $ ts` (Accounts) and `cs = ... concatMap
(amountsRaw . pamount) $ concatMap tpostings ts` (Commodities) are
computed from the identical `ts`. I then built a real fixture
(`/tmp/.../scratchpad/stats-commodity.journal` — a `$100` posting at
depth 3 and a EUR posting pair at depth 4) and ran the real, pinned
`hledger` 1.52.4 binary (`/home/cormac/.local/bin/hledger`):

```
$ hledger stats -v                 # no depth limit
Commodities         : 2 ($, EUR)
$ hledger stats --depth 3 -v
Accounts            : 2 (depth 3)
Commodities         : 1 ($)        # EUR (only present below depth 3) is DROPPED
```

Confirmed empirically, not just from source: hledger's real `stats
--depth N` excludes commodities that appear only below the depth cutoff
from the Commodities count, exactly the same exclusion mechanism as
Accounts.

## Ground truth I independently re-derived (Part 2)

Read `ledgerkit/query/depth.py`, `ledgerkit/reports.py` (`accounts`,
`balance`, `register`, `stats`), `ledgerkit/cli.py`, `tests/test_reports.py`.
`reports.py::stats()`:

```python
all_accounts = {p.account for t in txns for p in t.postings
                 if not account_excluded_by_depth(depth_spec, p.account)}
all_commodities = {p.amount.commodity for t in txns for p in t.postings
                    if p.amount is not None}   # <-- no depth_spec check at all
```

I ran the equivalent fixture through Ledgerkit's own CLI
(`.venv/bin/python -m ledgerkit.cli`, commit `c6168b2`):

```
$ ledgerkit stats -v                # no depth
Commodities         : 2 ($, EUR)
$ ledgerkit stats -q depth:3 -v
Accounts            : 2 (depth 3)
Commodities         : 2 ($, EUR)    # EUR should have been excluded — it wasn't
```

**Confirmed, live, on both sides: this is a real divergence**, not a
false positive. `all_commodities` in Ledgerkit's `stats()` is computed
without the same `account_excluded_by_depth` gate `all_accounts` uses,
so Ledgerkit's `stats -q depth:N` under-excludes: it correctly narrows
the account count/list but leaves the commodity count/list at its
undepth-limited value whenever some commodity appears exclusively on
postings deeper than the cutoff. I also confirmed
`tests/test_reports.py::test_stats_query_depth_excludes_rather_than_clips`
(line 1033) asserts only on `account_count`/`account_depth`, never
`commodity_count`/`commodities` — the gap is untested. And I read
Ledgerkit's own internal compatibility record
(`dev-docs/compat-register/LK-COMPAT-QUERY-DEPTH-STATS-001.yaml`,
`status: verified`) directly: **its own four live-comparison scenarios
all `grep -i account` only** — the record that the project itself treats
as authoritative proof of stats/depth compatibility never checked
Commodities either. This is a genuine, previously-unrecorded correctness
gap in Ledgerkit, not something already known and merely restated.

Everything else in both reports' Part 2 tables (balance/register/
accounts/print mappings, the `MaxAccountLevel` disclosed non-equivalence,
the "no standalone `--depth` flag in Ledgerkit" gap, the `-1` mechanism
divergence) checked out against source exactly as stated by whichever
report made the claim.

incompleteness rather than a fabricated claim — but it is a **material**

## Overall

**Overall verdict: PASS WITH GAPS.**
No incorrect or misleading claim was found in what CodeCompass itself
generated (the `CLAUDE.md`/`DEPTREE.md`/`FILETREE.md` digests, and the
correctly-scoped, commit-pinned source clones) — everything I checked
against the real target repositories held up, including the previously
disclosed §4 monorepo-scoping fix, now independently confirmed working.
The "gaps" here are about how little of the task's real work that
generated material actually did, not about it being wrong.

**Overall context advantage: LOW.**

**Outcome shape (§2.6, required)**: **(b) — helped Part 1 (navigation)
but not materially Part 2 (cross-language semantic recognition)** — and
even Part 1's "help" was marginal/navigational (LOW), not a
qualitative advantage over ordinary tools. This is exactly the shape the
amendment's authors said (b) was written to make legible, and it is what
actually occurred: the generated digests gave the treatment agent a
faster on-ramp to *which hledger files exist and what they're named*
(real, if modest, value — comparable to a good `find`/`grep`), but
contributed nothing to *understanding what those files' code does*
(zero depth-related content in the one digest that would have mattered
most) and nothing at all to the cross-language half, which ran entirely
on raw-source reading available equally to both conditions.

## §1.5 boundary restatement (required)

This evaluation, like the phase itself, tested **adapter-derived
context** (the generated `CLAUDE.md` symbol/purpose listings), **dependency
structure** (`hledger → hledger-lib`, confirmed present in both
vendors' `DEPTREE.md`), and **vendor-source grounding** (a real,
correctly-scoped, commit-pinned local clone of each vendor's own
source) — never graph-level Haskell symbol integration. I did not run
`codecompass query symbols`/`uses_edges` against either vendor, and
neither agent's report claims to have gotten anything useful from such a
command (treatment explicitly notes `codecompass` wasn't even
installed/on `PATH` in its sandbox and moved on, per the task's own
disclosed-limitation guidance). `CG-008` (empty `symbols` table for
Haskell vendors) remains Phase 62's own open question, untouched by this
result either way. A LOW rating here is not a claim that graph-symbol
integration would also be LOW-value — it's a claim about what the
adapter-derived digest content, on its own, contributed to this specific
task.

## Material gaps / failures

- **[Baseline, Part 2]** The `stats` row's "Matches" verdict does not
  address the Commodities field at all, and a real, live-confirmed
  divergence exists there. Not an explicit false claim (the field is
  simply never checked), but material given the task's explicit ask to
  "state explicitly any case where they diverge."
- **[Both, Part 1]** Baseline's "register — clip only (no aggregation,
  no exclusion)" is stated without the report-interval qualification;
  true only for the non-interval case. Minor, not misleading on its own,
  but a reader generalising from it would be wrong for `-M`/`-Q` usage.
- **[Treatment/CodeCompass]** `vendor/hledger/CLAUDE.md` — the one
  generated artifact most directly relevant to Part 1's command-level
  question — carries zero depth-related content and, more generally, no
  control-flow/business-logic detail for any function, only
  name+one-line purpose. This is a structural limit of
  `readme_and_api_surface()`'s current design, not a one-off omission;
  worth a candidate learning if it isn't already filed (adapter-generated
  digests answer "what exists and what's it called," not "what does it
  do internally").
- **[Methodology]** The two-agent, single-trial design cannot fully
  separate "CodeCompass's contribution" from "agent diligence variance"
  — the clearest example being the stats/Commodities finding, which both
  agents had equal raw evidence for and only one surfaced. This
  evaluation attributes that specific difference to agent variance, not
  to CodeCompass, precisely to avoid the instrument's own warned-against
  failure mode (crediting CodeCompass for outcomes it didn't cause).
  Future phases comparing single-trial agent pairs should treat any
  observed quality delta as a hypothesis, not a measured effect, unless
  the delta traces to specific generated content one condition had and
  the other didn't.
- **[Confirmed, not a gap]** The §4 `HaskellAdapter.repository_url()`
  subdirectory fix is real and independently verified working (correctly
  scoped `CLAUDE.md` content for both vendors from a single, larger,
  by-design-unscoped physical clone).

## Would this have misled the implementing agent? partially

If an implementer trusted **baseline's** Part 2 report as the complete
picture, they would be misled: Ledgerkit's `stats -q depth:N` really
does under-exclude commodities relative to hledger's real behaviour, and
baseline's report gives no indication of this. If an implementer worked
from **treatment's** report, they would not be misled — the divergence
is disclosed, correctly grounded, and appropriately hedged about not
being independently re-run live (which I have now done, and it holds).
Since this evaluation covers both conditions together and the
misleading gap sits on the *no-CodeCompass* side, it is not a criticism
of CodeCompass's own output — but it is a genuine, real risk in this
specific experiment's evidence base that any consumer of "baseline
agent said it matches" should not treat as settled.
