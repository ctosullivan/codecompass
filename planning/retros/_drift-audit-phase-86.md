## Verdict: DRIFT — 2 findings, both non-blocking (stale-by-omission, fixed same day)

No current-truth doc makes a statement about Phase 86's script that is actively **false**; both findings are omissions that make a previously-complete-reading catalog now incomplete relative to the corrective pass (`e796b08`), which updated the script's own code and docstring but no narrative doc alongside it.

### Finding 1 (non-blocking, fixed) — `docs/development/contributing.md`, "Maintainer-only tooling" entry for `scripts/check_knowledge_placement.py`, line 30

The entry's exception-set claim — "A per-file `SyntaxError`/`OSError`/`tokenize.TokenError` produces an always-blocking `knowledge-placement-unparseable-source-file` diagnostic" — omits `UnicodeDecodeError` and `IndentationError`, both of which the current code also catches for this same diagnostic (`_extract_file_citations`: `except (OSError, UnicodeDecodeError)` for the read, `except (SyntaxError, tokenize.TokenError, IndentationError)` for the parse). More significantly, the entry names only **one** diagnostic (`knowledge-placement-unparseable-source-file`) and never mentions the second one the corrective pass added: `knowledge-placement-unreadable-decision-file` (always-blocking, raised in `_build_superseded_map` when a `decisions/*.md` file cannot be read or decoded). This is a whole rule the entry's catalog omits, not merely an incomplete exception list. Confirmed by direct inspection of `scripts/check_knowledge_placement.py`'s own docstring's "Diagnostics" section, which lists both, against contributing.md's text, which lists only the first. Non-blocking: nothing existing is false, the entry just no longer describes a complete picture of the script's diagnostics.

**Fixed** (same day): widened the exception list and added the second diagnostic to the entry's prose.

### Finding 2 (non-blocking, fixed) — `docs/concepts/knowledge-placement-policy.md`, "How this is enforced today" section, lines 66-71

"`scripts/check_knowledge_placement.py` — two mechanical checks (...) plus an always-blocking parse-failure diagnostic." The phrase "an always-blocking parse-failure diagnostic" (singular) was accurate against the original implementation but is now incomplete: the corrective pass added a second, differently-scoped always-blocking diagnostic (`knowledge-placement-unreadable-decision-file`, about the ADR corpus being unreadable, not about a *source file's* parse failure). The sentence is softened by "See the script's own module docstring for the exact extraction method" immediately after, which mitigates but does not erase the omission — a reader relying on this page alone would not learn a second diagnostic class exists. Non-blocking, same stale-by-omission character as Finding 1.

**Fixed** (same day): rewrote the sentence to name both diagnostics' distinct scopes (source-file parse failure vs. ADR corpus unreadability) without enumerating full exception lists here (left to the script's own docstring).
