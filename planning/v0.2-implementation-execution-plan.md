# MVP (v0.2) implementation execution plan

Not a roadmap phase itself — an operating procedure for actually building
phases 10-19, written because doing all ten in a naive "just keep going"
mode risks losing fine-grained state to context compaction long before
the arc finishes. This file is the durable checkpoint a compacted or
restarted session reads to resume correctly; `planning/CONTEXT.md` stays
the source of truth for exact current position (per `CLAUDE.md` §4), this
file is the *procedure* both this session and any future one follows to
get there.

## Why this needs a strategy, not just execution

- Ten phases, each touching multiple source files, new modules, tests,
  and docs — reading every file involved in every phase, in one
  continuous context, would accumulate far more than needs to stay live
  at once. Compaction is designed to handle that gracefully, but
  compaction summarizes; it doesn't reliably preserve exact function
  signatures, subtle "why this and not that" reasoning, or partial
  in-progress edits the way a fresh, tightly-scoped context does.
- The phases are strictly sequential (confirmed repeatedly while writing
  their plan files — Phase 12 extends Phase 11's call site, Phase 15
  assumes 10-14 already exist as libraries, Phase 16 is only safe once
  15 removes every other `Depth` consumer). No parallelism is available;
  the risk isn't "how do I do these faster," it's "how do I do ten
  sequential things without the tenth being planned/executed against a
  degraded understanding of the first."
- A prior incident this session (a research subagent deleted files
  despite explicit read-only instructions, root-caused to unrestricted
  Bash access) is the concrete reason the per-phase pattern below
  includes independent verification after every delegated step, not
  trust in a subagent's own completion report.

## The pattern, per phase (10 through 19, strictly in order)

1. **Dispatch one implementation subagent per phase**, `subagent_type:
   general-purpose`, foreground (`run_in_background: false` — the next
   step strictly depends on this one's result, so there's nothing useful
   to interleave while waiting). The prompt is self-contained: the exact
   phase plan file path (`planning/phase-N-*.md`, already
   implementation-ready — Scope, Design decisions, Files, Verification
   all written out), explicit instruction to implement exactly what it
   scopes (no more), write/update the tests it specifies, run `pytest`
   and `ruff check .` itself, and report pass/fail plus a summary of
   what changed. This keeps the *bulk* of each phase's context (reading
   five source files, iterating on an implementation, re-running tests
   while fixing a bug) inside that subagent's own isolated context
   rather than accumulating in this orchestrating session's transcript.
2. **Independently re-verify — never trust the report alone, and never
   trust green tests alone either.** Run `pytest` and `ruff check .`
   again from the orchestrating session after the agent reports done.
   Run `git status`/`git diff --stat` and confirm the changed-file list
   matches that phase's plan file's "Files" section — no scope creep
   into files that plan didn't name. **Then actually read the diff for
   the phase's core logic change, not just the test output.** Phase 13
   is the concrete proof this step earns its keep: a real bug (a
   `depth = surface` vendor's clone failure leaking into a misleading
   "Description unavailable" section it was never eligible for) passed
   `pytest` and `ruff` cleanly — no test had ever asserted the *absence*
   of that section for that specific combination, because nothing before
   Phase 13 could produce it. It surfaced only from reading
   `sync.py`'s diff and reasoning forward through `claude_md.py`'s
   rendering logic, not from any automated signal. A clean test run
   confirms nothing regressed against what was already tested; it says
   nothing about a new code path nothing yet tests.
   This is the direct, concrete lesson from this session's earlier
   subagent incident: verify independently, every time, not just when
   something feels off.
3. **Same-commit docs** (`architecture/overview.md`, `docs/*.md`,
   `decisions/*.md` if that phase's plan calls for a new ADR) — the
   subagent's task already includes these per its plan file's own Files
   section; the orchestrating session spot-checks them rather than
   re-authoring them.
4. **Orchestration bookkeeping, done directly by this session, not
   delegated**: `planning/ROADMAP.md` (flip that phase to `done`),
   `planning/CONTEXT.md` (overwrite current-state section — current
   phase, what was just completed in 2-3 sentences, next concrete step),
   `CHANGELOG.md` (one entry, this phase only, per `CLAUDE.md` §3). Kept
   undelegated because this bookkeeping *is* the cross-phase state a
   compacted/resumed session depends on — it needs to be authored with
   full knowledge of exactly where the arc stands, not reconstructed by
   a subagent that only saw one phase.
5. **One commit, `feat(phase-N): summary`, then push.** Every phase lands
   as its own commit — if phase N+3 turns out to have a problem, phases
   up to N+2 are already safely on `main` and reverting just the bad one
   is a normal `git revert`, not a large, entangled rollback.
6. **Only then move to phase N+1.**

**Stop-and-ask condition, carried from `CLAUDE.md` §1 and restated here
because it must survive the delegation pattern above**: if a phase's
actual implementation surfaces an assumption its plan file didn't
already settle, pause and ask before proceeding — whether that surfaces
inside the subagent's work (it should say so in its report rather than
guessing) or only becomes apparent during the orchestrating session's own
verification pass.

## Context-management specifics

- **Terse per-phase status in the visible conversation.** A short "Phase
  N done, tests green (`pytest`: N passed), committed `<hash>`" — not a
  re-paste of the full diff or test output. Git history is the detailed
  record; the conversation only needs to carry forward *decisions*, not
  transcripts, matching how this session has already been operating for
  phases 9 and 10.
- **`planning/CONTEXT.md` is the actual resumption mechanism**, not this
  file's prose. If this conversation compacts mid-arc, or a future
  session picks this up cold, the correct recovery path is: read
  `planning/CONTEXT.md` for exact current position, read
  `planning/ROADMAP.md` for what's `done` vs `planned`, read `git log`
  for the detailed history, then read the *next* unimplemented phase's
  plan file in full before touching anything — not attempt to recall
  this conversation's earlier turns.
- **Never batch multiple phases into one subagent dispatch**, even
  though it would reduce orchestration overhead — it would reintroduce
  exactly the "too much in one context" problem this plan exists to
  avoid, and it breaks the one-phase-one-commit safety property in item
  5 above.
- **No worktree isolation for these dispatches** (unlike the
  recommendation left in `planning/CONTEXT.md` for *research* subagents)
  — these agents' entire purpose is to modify the working tree; isolating
  them would just add merge overhead for no safety benefit, since the
  actual safeguard here is independent post-hoc verification (step 2),
  not sandboxing.

## Expected shape of this work

Ten phases of real implementation is a multi-turn, likely multi-session
effort — that is the expected outcome of following this plan, not a
shortfall. Each phase completing cleanly, verified, committed, and
checkpointed in `planning/CONTEXT.md` is the actual unit of progress;
finishing all ten in one continuous run is not the goal this plan
optimizes for.
